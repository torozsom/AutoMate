# Deployment telemetry rollout and verification

## Configuration and topology

Web startup in both SelfHosted and SaaS requires `TelemetryStorage:Backend=LokiMimir` and `DeliveryMode=DiskGateway`.
Configure all three
Loki/Mimir endpoints, `GatewayUrl` and a shared random `GatewayToken` through private environment settings/Key Vault.
`GatewayUrl` is the separate Telemetry service's base URL, not Loki's Nginx gateway. Preserve TLS verification;
`CaCertificatePath` optionally adds a private public CA to the telemetry client only. No endpoint/token is committed.

Run `Telemetry` privately with the same application database connection, backend endpoints and ingestion token,
plus `DiskSpool:Directory=/var/telemetry` on an encrypted persistent disk. It reads project policies and writes daily
statistics, but never writes raw diagnostics to PostgreSQL. Web hosts the legacy database outbox worker until old
payloads drain. SeaweedFS/Loki/Mimir remain the existing self-managed store topology; production replication and
backup capacity are operator provisioning, not automatic consequences of enabling this mode.

For the existing local pilot, put `TELEMETRY_DATABASE_CONNECTION` and a freshly generated `TELEMETRY_INGEST_TOKEN` in
the ignored `.telemetry/pilot/compose.env`, then combine `compose.yaml` and `compose.disk.yaml` with the telemetry
profile. The connection hostname must be reachable from the telemetry container (for local Docker Desktop development,
use the appropriate host gateway). The override exposes ingestion only on loopback port 9450. Web's local gateway
URL is `http://localhost:9450`; enable `AllowInsecureDevelopment` only for this private development setup. Existing
Loki/Mimir TLS endpoints can still be used by Web. Production ingress must be private HTTPS.

## Migration and rollout

1. Apply `AddSaaSTelemetryAnalytics` and `AddCloudTelemetryCollectorLeases` using normal Web migrations. No existing
   diagnostic payloads or deployment identities are rewritten.
2. Start the single telemetry service after migrations. Verify authentication, volume ownership, a durable receipt,
   restart recovery, `/status` and actual Loki/Mimir visibility with a canary account.
3. Enable DiskGateway on a limited audience. In both profiles, invalid gateway configuration fails startup; missing
   managed
   consent does not trigger a raw PostgreSQL fallback. Policy/consent caches expire after five seconds.
4. Keep the old database outbox worker running until pending database payloads reach zero. Existing 30-day database
   history is merged with pending disk and confirmed backend history. V1 APIs stay available; v2 log cursors are
   versioned and resource-scoped. Do not downgrade an AutoMate host to a raw database fallback during an outage.
5. Roll out updated workflow/Bicep templates before new monitored deployments. They use `am-{github.run_id}` revision
   suffixes. Existing cloud deployments require a verified persisted resource/revision mapping or redeployment to
   obtain restart recovery; do not guess an old deployment's revision from a newer deployment's app state.

## Data and UI

`GET /api/v2/projects/{project}/deployments/{deployment}/logs` accepts bounded cursor/search/limit parameters; it never
accepts arbitrary LogQL. Searches are escaped literal filters. Legacy PostgreSQL rows retain their old numeric
positions.
New positions are generated by the spool, not a database sequence; envelopes carry stable event IDs. Pending reads
are capped at 2000 events and expose truncation. Search matches the stored log JSON; legacy/pending messages use literal
message matching. A storage failure prevents the replay cursor advancing.

`GET /api/v2/projects/{project}/analytics?start=<UTC>&end=<UTC>` exposes at most 10,000 daily rows over at most 365
days.
Project details shows counts, weighted observed-sample averages, daily charts with gaps and bounded daily tables with
links to deployment
charts/log search. Cloud duration includes queue time and uses completed cloud run timestamps; local duration is absent
rather than inferred from mutable status timestamps. Missing samples stay gaps. Observed log error counts are
approximate.

Daily aggregation runs hourly on the single telemetry service, replacing current/previous-two-date results. It uses
Mimir count/sum/min/max queries, never averages averages. It does not backfill unavailable history. Keep detailed data
30 days, daily data 365 days, and apply those deadlines to encrypted backups and restored copies too.

## Verification

Run `dotnet test AutoMate.slnx` and `dotnet format AutoMate.slnx --verify-no-changes`. Credential-free coverage includes
spool durability/recovery/corruption/exclusive ownership/quota rejection, resource-scoped cursors, no raw PostgreSQL
insertion/fallback, authorization, durable-only Azure checkpoints and aggregate replacement/retention.

The spool load test covers 300 deployment identities, 100 logs/s for five seconds and 1000 logs/s for two seconds,
using 1 kB messages. Its result is written under the ignored test `bin` directory. It measures local durable ingestion,
not end-to-end backend capacity or sustained production load. Run the existing disposable integration Compose tests
only when `AUTOMATE_TELEMETRY_TEST_DB` points to the disposable database; never an application database. Before public
rollout, measure gateway HTTP, provider throughput, collector backlog and retention/recovery under actual
infrastructure.

Delivery retries use bounded exponential delays (2–300 seconds); expiry sweeps run independently of backend
availability. /status exposes backlog, age, bytes and drop counts. Rate windows restart with the ingestion process;
durable byte quotas and dropped-event counters survive restart. The initial load test is a brief ingestion benchmark,
not the final sustained 300-deployment production acceptance run.

An extended local benchmark also runs with AUTOMATE_TELEMETRY_EXTENDED_LOAD=1: 60 seconds at 100/s followed by 10
seconds at 1000/s. See telemetry-load-results.md. All six isolated PostgreSQL/Loki/Mimir integration tests were
executed, including recovered disk delivery, raw-row avoidance, daily metric queries and tenant isolation.
